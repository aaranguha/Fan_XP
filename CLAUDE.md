## 1. What this is

**Fan XP finds empty ("no-show") seats at sporting events in real time, and
connects fans in the building with those seats for the second half.**

The core insight: a ticketing platform knows who *bought* a seat. It has no
idea who actually *sat in it*. That gap — sold but empty — is real, measurable,
and currently invisible to teams, broadcasters, and fans. Fan XP measures it
using nothing but public secondary-market data (no integration with a team's
ticketing system required), and turns it into two things:

1. **A sales product for teams**: per-team dashboards showing real no-show
   counts, "phantom revenue" (lost concession/atmosphere value), and
   section-level breakdowns — a data product a team can act on.
2. **A fan product**: a live app where a fan already at the stadium can claim
   a real empty seat for the second half, pay for it, and the seat's actual
   owner (a season ticket holder or reseller) gets a text asking to confirm
   the release for a stadium-credit payout.

**Methodology**: capture the secondary-market (resale) listings for a venue
twice — once ~60 minutes before kickoff/first pitch/tip-off (the baseline: what's
for sale), and again mid-event (currently: NFL ~45 min post-kickoff, other
leagues have their own timing). A seat listed in *both* snapshots was never
claimed or sold to anyone who showed up — that's a confirmed no-show. The
diff between the two snapshots is the whole product.

their dedicated runner machine is sitting ready (see §5).

expanding to college football later (feasibility already checked — Ticketmaster's
API returns college football events under the same query the NFL runner uses;
would need a new team/venue config, no new architecture). Pitch materials
should lean on the *methodology* being proven (via MLB/WNBA's real historical
captures) since NFL itself has very little real captured data yet — the season
just started.

**Standing decision — no auction/bidding**: a 60-second live-bidding auction
system was fully built and tested earlier in this project's life, then
explicitly reverted at the founder's request ("let's just have the fixed
price set — we can always add the auction part later if needed"). **Do not
reintroduce auction/bidding logic unless explicitly asked again.** The fan
flow is fixed-price: a fan sees a price, pays it (Stripe auth, captured only
on seller confirmation), done.

## 4. The data pipeline, in detail

### 4.1 Scraping core (`scraping/fetch_listings.py`)

Shared by all four leagues. `scrape_listings(event_url, ...)` opens a real
(non-headless on macOS) Playwright browser against a live Ticketmaster event
page and intercepts three XHR calls: inventory facets, pricing facets, and
places (seat-level) facets. Returns `(facets, offer_price_map, places_facets,
embedded_offers)`.

**Critical, hard-won fact about `embedded_offers`**: as of ~September 2026,
Ticketmaster removed the `"section"` field from both the inventory and places
facets responses, which silently broke the old price-to-seat join logic
(confirmed live: 0 of 1228 scraped rows had a price, despite the underlying
price data existing correctly elsewhere). The fix — and now the *primary*
data path — is `build_rows_from_embedded_offers()`, which uses the inventory
response's `_embedded.offer` array (present because the inventory URL
requests `embed=offer`). Each embedded resale offer object carries `section`,
`row`, `seatFrom`/`seatTo`, and price together on the same object, so it needs
no cross-referencing at all. **If prices ever come back empty/None again,
check whether TM changed this response shape again before assuming the old
facet-matching code (`parse_seats`/`parse_facet`, still present as a fallback)
is the problem — it almost certainly isn't the primary path anymore.**

`scrape_from_endpoints()` is a faster re-fetch path (no page navigation, reuses
captured XHR URLs+headers) used only by NBA's halftime re-scrape, to avoid
re-triggering TM bot detection by reloading the page.

### 4.2 Per-league runners

- `nfl_run_game.py` — the most actively developed. Usage:
  `python nfl_run_game.py <team_slug> [YYYY-MM-DD]`. Sleeps until
  `kickoff - 60min` (pre-game scrape), then waits for the second snapshot
  trigger, then scrapes again, compares, and writes to Supabase.
- `mlb_run_game.py`, `wnba_run_game.py` — same shape, different timing
  constants and ESPN/stats-API endpoints for their own live-clock detection.
- `run_game.py` — NBA's (older, more complex; combines geometry + story).
- `nfl_runner.py` / `mlb_runner.py` / `wnba_runner.py` / `daily_runner.py`
  (NBA) — the daily entry points GitHub Actions actually invokes. Each finds
  today's home games via the relevant API and launches one `*_run_game.py`
  subprocess per team, in parallel. **After a team's run succeeds**, the NFL
  runner automatically regenerates that team's dashboard AND interactive seat
  map (see §4.4), then commits and pushes — this is why a real capture shows
  up on the live site automatically, no manual step required.

**Second-snapshot timing, and why it matters more than it sounds**:
- NFL: `HALFTIME_FALLBACK_MIN = 45` (minutes post-kickoff). **This was 70,
  then lowered to 45 on 2026-09-09** after the first real NFL game
  (Seahawks vs Patriots) showed Ticketmaster's own resale listings had
  already collapsed from 181 (pre-game) to 4 real seats by the 71-minute
  mark, and were fully gone (0) hours after the game ended. This strongly
  suggests **Ticketmaster's marketplace itself winds down/closes listings as
  an event proceeds** — not fans failing to show up. 45 minutes is a first
  estimate for roughly halfway through Q2, erring early on purpose. **This
  needs to be re-evaluated after the next real NFL Sunday (2026-09-13, 13
  home games at once) — watch whether 45 min meaningfully improves data
  yield, or whether it needs to move even earlier.**
- ESPN's live scoreboard API (`site.api.espn.com`) is **confirmed blocked**
  (HTTP 403) from the runner machine itself (verified via the smoke-test
  workflow, not just locally) — so NFL and WNBA, which both try to use ESPN
  for precise live-clock detection, always fall back to their fixed-minute
  timer in practice. Only MLB gets real live-clock detection, because it uses
  `statsapi.mlb.com` instead of ESPN.
- A **plausibility gate** now exists in `nfl_run_game.py`
  (`MIN_HALFTIME_RATIO = 0.15`): if the halftime listing count is below 15%
  of the pre-game count, the code treats this as "marketplace collapsed, not
  real attendance data" and **skips the no-show insert entirely**, sending a
  Telegram explanation instead of recording a fabricated near-100% no-show
  rate. This directly followed the incident above — do not remove this gate
  without a good reason; it is the only thing standing between "TM closed the
  marketplace" and a wildly misleading dashboard number.

### 4.3 Data-integrity bugs found and fixed (worth knowing so history doesn't repeat)

- **Duplicate-insert bug**: `insert_listings()`/`insert_no_shows()` in
  `supabase_client.py` used to blindly insert every time they were called.
  If a game got processed twice (overlapping cron triggers on the same day —
  Sunday fires two NFL triggers; MLB fires up to 6x/day — or a runner re-run
  that reloads its own already-scraped local CSV), the same rows got inserted
  again. **Confirmed in production**: one real Diamondbacks MLB game had
  105,192 "no-show" rows recorded — physically impossible for any stadium.
  Fixed: both insert functions now check for existing rows first and no-op if
  the game/snapshot already has data. **MLB's historical data before this fix
  may still contain corrupted games** — any code that aggregates MLB
  no-show/phantom-revenue totals should filter outliers (see
  `MAX_SANE_NO_SHOWS` pattern in `generate_capability_statement.py`) until
  someone goes back and cleans the historical rows.
- **`halftime`/`mid_game` naming mismatch**: `nfl_run_game.py` writes the
  second snapshot as phase `"halftime"` (matches WNBA's convention), but
  `generate_nfl_story.py` used to read phase `"mid_game"` (MLB's convention).
  This would have made every NFL dashboard show "no data" forever, even after
  a fully successful real capture. Fixed — verify any *new* NFL-related code
  uses `"halftime"`, not `"mid_game"`.
- **Supabase `.maybe_single()` quirk**: in the installed postgrest-py version,
  `.maybe_single().execute()` returns `None` itself (not a response object
  with `.data = None`) when zero rows match. `fanxp_app/fanxp_api.py` has a
  `fetch_one()` helper that handles this correctly — use it, don't call
  `.maybe_single().execute().data` directly, it will crash on a miss.
- **Seat-map section click-through gaps**: the interactive seat-map pages
  (`docs/nfl_{slug}_seatmap.html`) used to try to color/attach click handlers
  to Ticketmaster's own background SVG art by matching section names against
  element `id`s. TM's own SVG export turned out to use *several different,
  inconsistent* id schemes across sections in the same venue (plain `"116"`,
  `"Shape116"`, `"116 lvl"`, or split into unlabeled multi-fragment paths like
  `"340X96"`/`"340X155"` for large curved sections) — and for roughly a third
  of real sections, no shape existed in their art at all. **The fix, now the
  permanent architecture**: `extract_stadium_geo.py` computes each section's
  own shape directly from its real seat coordinates (a minimum-area bounding
  rectangle around a convex hull of the seats, with a small outward pad), and
  `build_stadium_seatmap.py` draws these as our own SVG paths, completely
  independent of Ticketmaster's background art id scheme. Verified via a real
  headless browser (not assumption) at 100% section coverage for two
  different venues (Lumen Field, Lambeau Field) after this change. **Do not
  go back to id-matching against TM's background art** — it fundamentally
  cannot reach 100% coverage because the art itself is missing shapes for
  real sections, not because the matching logic was incomplete.

### 4.4 Dashboards and seat maps (generated output)

- `generate_nfl_story.py`, `generate_mlb_story.py`, `generate_wnba_story.py`,
  `generate_nba_dashboard.py` — one per league, output
  `docs/{league}_{team}_story.html` (or `_dashboard.html` for NBA). Each
  shows: games tracked, total no-shows, avg no-show rate, avg seat value,
  total/avg "phantom revenue" (`no_show_ticket_value + no_show_count * $35
  concession estimate`), a game log table, and a top-no-show-sections table.
  All four follow the same light editorial design system (see §7). NBA has
  its own generator (not folded into the others) specifically to avoid
  touching `generate_team_story.py` (see below).
- `generate_team_story.py` — NBA's older, separate, more complex generator
  that combines the interactive seat visualization *and* dashboard content
  into one page (`docs/{team}_seat_story.html`). This is architecturally
  different from the other three leagues (which split "dashboard" and
  "interactive map" into separate pages) and was deliberately left alone
  when NBA got its own dashboard generator, specifically so the existing,
  working interactive visualization wouldn't be disturbed.
- `extract_stadium_geo.py` + `build_stadium_seatmap.py` — NFL's interactive
  seat map (`docs/nfl_{slug}_seatmap.html`). See §4.3 for the section-shape
  architecture. When a team has no real completed game yet, sections render
  in a clearly-labeled **preview state** — a deterministic (seeded), honest
  spread of ~22% of lower-bowl sections marked "open," with a legend that
  explicitly says "Empty — preview only" and copy stating "availability shown
  is a preview." **Never remove that labeling** — it's the line between an
  honest placeholder and a page that looks like it's showing real fan data
  when it isn't.
- `generate_capability_statement.py` — the one-page sales collateral
  (`capability_statement.html`, root of repo, NOT in docs/). Fully generic
  (no team name baked in — this was explicitly requested after an earlier
  version was Commanders-specific and had gone stale). Pulls live numbers
  from Supabase each time it's run. **Deliberately excludes MLB from its
  "proof of concept" stats** (`MAX_SANE_NO_SHOWS = 500` filter) because of
  the duplicate-insert corruption described above — only cites sanity-checked
  NBA/WNBA numbers. If you ever want to include MLB numbers in pitch
  material, first confirm the historical corrupted rows have actually been
  cleaned from Supabase, don't just trust the filter to keep working forever
  as more real data accumulates.

## 5. Infrastructure

**Self-hosted GitHub Actions runners** (required — Ticketmaster bot-blocks
GitHub's own hosted-runner IP ranges, confirmed via a live 403):

- `intel-mac-runner` — labeled `nfl-runner`. Currently the **sole runner for
  NFL** (label was deliberately moved here from `nfl-mac-runner` at the
  founder's request). `nfl.yml` targets `runs-on: [self-hosted, nfl-runner]`.
- `nfl-mac-runner` — labeled `shared-runner`. Reserved for MLB/WNBA/NBA
  (currently idle since those workflows are disabled). This machine used to
  silently miss every MLB/WNBA/NBA job for an extended period because it was
  never actually registered with the `shared-runner` label the workflows
  require (a runner *being online* and a runner *having the label a workflow
  needs* are two independent things — always check both when a job seems
  stuck `queued`).
- Runner labels can be added/removed via the GitHub API
  (`POST/DELETE .../actions/runners/{id}/labels/...`) without touching the
  physical machine at all — this is how the reassignment above was done.
- `smoke-test.yml` — a standalone, manual-dispatch-only workflow
  (`gh workflow run smoke-test.yml`) that runs a real live scrape against a
  given Ticketmaster event URL, on the actual runner, with zero writes to
  production data/Supabase. Use this to test whether a specific runner's
  network/environment can actually reach Ticketmaster (or ESPN) *without*
  disturbing whatever real job might currently be sleeping on that runner —
  though since a self-hosted runner only handles one job at a time, testing
  this way means briefly canceling any in-progress real job and re-triggering
  it afterward (`gh workflow run nfl.yml` again) once the smoke test finishes.
- **Job timeout lesson**: `nfl.yml`'s `timeout-minutes` has been raised twice
  — 360 → 720 → 1440 (24h). Each time, a real scenario killed the job before
  it reached its actual work: first a late-firing scheduled trigger, then a
  same-day manual restart hours before a late kickoff. **Whenever you
  manually cancel-and-restart the NFL job** (e.g., to deploy a code fix, or
  to run a smoke test), remember the new job's clock starts over — if you do
  this early in the day before a late primetime kickoff, make sure the
  timeout still covers the gap.

**Supabase**: the single source of truth (`games`, `listings`, `no_shows`
tables) for all four leagues. **Real risk, already happened once**: Supabase
free-tier projects auto-pause after roughly a week of inactivity. This
happened mid-project (compounded by MLB/WNBA/NBA being paused and NFL not
having games every day) and took the *entire* product down — Supabase itself,
the deployed Render API, and every dashboard. Resuming it from the Supabase
dashboard ("Restoration in progress") took over 20 minutes for this project's
data size. **If anything reports Supabase as unreachable, check the dashboard
for a paused project before assuming a code bug.**

**Render** (`fanxp-api.onrender.com`): hosts `fanxp_app/fanxp_api.py`.
Free tier — cold-starts after inactivity (can take 30-60s for the first
request). Auto-deploys on push to `main` (confirmed: picks up new commits
within about a minute). Needs its own env vars set manually in the Render
dashboard (see `render.yaml` for the current list); a new secret being added
to `.env` locally does **not** propagate there automatically.

**Vercel** (`fan-xp.vercel.app`): hosts everything in `docs/`. Auto-deploys
on push to `main`. Static only, no server-side logic.

**GitHub repo**: `aaranguha/Fan_XP`, currently **public**. This is a live,
undecided risk for GTM — the full methodology, phantom-revenue formula, and
(depending on what's committed) real captured team data are visible to
anyone, including any team being pitched or any competitor. Not yet decided
whether to make it private; flag this to the founder if it comes up again.

## 6. The fan-facing product (`fanxp_app/`)

`fanxp_api.py` is a Flask app with two parallel flows:

1. **Generic/demo flow** (`/api/empty-seats`, `/api/seats/<id>/request`,
   `/webhooks/twilio/sms`) — the *original* build, backs the now-orphaned
   `docs/fanxp_app.html` (nothing on the live site links to it anymore).
   Uses `sth_seat_assignments`, a table only populated by manually running
   `seed_mock_game.py` — not connected to the live scraping pipeline at all.
   Treat this as legacy/demo-only, not the real product surface.
2. **NFL-specific flow** (`/api/nfl/<slug>/request`,
   `/api/nfl/requests/<id>`, `/api/nfl/requests/<id>/respond`,
   `/nfl/respond/<id>`, part of `/webhooks/twilio/sms`,
   `/webhooks/stripe`) — this is the **real, current product**, backing
   `docs/nfl_{slug}_seatmap.html`. This is what should be demoed.

**Payment flow**: Stripe Checkout Session created with `capture_method:
manual` — the fan's card is authorized immediately but not charged. Only
when the seller (season ticket holder / reseller) replies YES (via a
tap-to-confirm link in an SMS, or the dry-run-mode `/respond` JSON endpoint)
does `PaymentIntent.capture()` actually charge the card. A NO reply or a
30-minute timeout cancels the hold instead. **Both capture and cancel calls
are wrapped in try/except** (added after a live rehearsal exposed an
unhandled Stripe failure crashing the whole respond flow) — a failed capture
leaves the request in `seller_pinged` rather than falsely marking a seat
confirmed that was never actually paid for.

**Twilio**: `TWILIO_DRY_RUN=true` currently (both locally and on Render) —
SMS is logged, not actually sent. Real delivery needs A2P 10DLC business SMS
registration with Twilio before going live with a real pilot — this has its
own real lead time, start it well before it's actually needed.

**Telegram bot** (`t.me/FanXP_bot`): two features, both wired into the
existing pieces above rather than being a separate system —
1. **Scrape status alerts**, sent from `nfl_run_game.py` at the pregame and
   halftime steps. Scoped to: any 49ers game, OR any "primetime" game
   (kickoff ≥ 7 PM ET, covers SNF/MNF/TNF and one-off evening games like the
   season-opening Wednesday game) for *any* team. Reports success (seat/price
   counts) or the actual error on failure. See `notify_scrape_status()` /
   `is_primetime()` in `nfl_run_game.py`.
2. **Natural-language Q&A** about empty seats ("what are the best sections?",
   "what's open in 101-104?") via a webhook (`/webhooks/telegram` in
   `fanxp_api.py`) that Telegram calls when a message arrives. Pulls real
   `no_shows` data for the most recent 49ers game (falls back to `pre_game`
   listings, clearly caveated as "not yet confirmed empty," if halftime data
   doesn't exist yet), hands it to **OpenAI's `gpt-5-nano`** (chosen as the
   cheapest available model — $0.05/1M input tokens), and relays the answer
   back. **Important gotcha**: `gpt-5-nano` needs
   `reasoning_effort="minimal"` explicitly set, or it can spend its entire
   token budget on internal reasoning and return an empty response
   (confirmed live: `finish_reason: "length"`, 0 output text, before this was
   added). One-time webhook registration lives in
   `fanxp_app/set_telegram_webhook.py`; run it again only if the webhook URL
   or secret ever changes.
   Both the bot token and Telegram chat ID, and the OpenAI key, live in
   `.env` locally and as GitHub Actions / Render secrets — never in the repo.

## 7. Site design system

Light, editorial theme across the marketing site, all dashboards, and the
capability statement (explicitly **not** applied to the NFL claim/seatmap
page, which was deliberately kept as-is per an early instruction — "keep the
selecting ticket page the same for now" — though the seatmap page has had its
own internal fixes since, just not a visual redesign).

Tokens: `--bg:#fafaf9; --surface:#ffffff; --border:#e7e6e2; --text:#16181c;
--muted:#6d7076; --muted-2:#9a9da3; --accent:#2f5fff (site) or team color
(dashboards)`. Fonts: Newsreader (serif, headlines, weight 500 — swapped from
Fraunces after its italic/"f" glyph looked broken at display sizes),
Inter (sans, body/UI), IBM Plex Mono (tabular numbers/stats). No
glassmorphism, no em dashes, no literal 3-column feature grids, no AI-tell
patterns generally — this was an explicit cleanup pass early in the project
after auditing against a "looks vibecoded" checklist.
